## Scope decisions made 2026-09-09, before any code

Timebox: 2 weeks max including testing. Backend: mocked, not blocking — develop and test against the OpenAPI contract's mock server; the real backend arrives on its own schedule and testing does not wait for it.

- **Chat/messaging (BRD story S-21) is cut** for this iteration.
- **Meetup ("share a place", S-17) is built reduced**: a one-way place-share object outside any conversation thread, not a message type. The full BRD version (R-70, R-117, business rule BR-03 of S-17) specifies the place card as a message living inside a 1:1 conversation, which isn't being built.
- **Push notifications and movement/geofence notifications (S-20, S-22) are deferred.** No device-token registration exists anywhere in the app yet. Per BRD business rule BR-06 (S-11), in-app entry points (the friend list's pending-requests badge) are sufficient without push, so this is safe to defer.
- **Friends layer on the map**: build the BRD's own documented fallback from day one — a toggle inside this feature's own bottom sheet — instead of waiting to confirm whether `features/lifestyle_layers/`'s existing map layers control can accept a new entry (open decision D-13, owner/timeline unconfirmed). Abstract the toggle so swapping to a real layers-control entry later doesn't require rewriting the map screen.
- **Friend positions start as polling** (`GET /v1/friends:positions` every 10-15s) behind an interface, not the full WebSocket channel from the API description. Upgrade later by copying `features/share_eta/providers/eta_websocket_locator.dart`.
- **QR code scanner is in scope for the MVP**, not a stretch item, built from scratch (old scanner code in the app is commented out / removed from dependencies).
- **First thing to cut if part B runs over time**: joining via invite link when the recipient has no app installed yet (store fallback + applying the invite after install, BRD story S-08). Nothing in the app handles that case today.

Full rationale for each of these is in the roadmap artifact above.

### What the requests-response slice actually built

- Both mocked repositories that hold real mutable state (`friendsRepositoryProvider`, `friendRequestRepositoryProvider`) were switched from plain `@riverpod` to `@Riverpod(keepAlive: true)`. This was a **real bug caught before it shipped**, not a stylistic choice: `friendsListProvider`/the requests providers only kept their repository alive via a `ref.watch` dependency edge that existed *only while a screen was actively watching them* — an accepted friend or a cancelled request would have silently reverted the moment the user navigated away and the underlying auto-dispose repository provider was torn down and rebuilt from its seed data.
- `FakeFriendRequestRepository` seeds **two fixed fake incoming requests** ("Fatima Al-Zahrani", "Khalid Al-Ghamdi") — there's no second real account in a single-device mock to be the sender of an incoming request, same reasoning as the 3 seeded sample friends.
- Outgoing requests (from Scan/deep-link) now carry a **deterministically fabricated display name** (hashed from the token into a small fixed name list) instead of being bare tokens — a real backend's resolve response would include the invite owner's real identity; this is the closest a mock can get without one. `resolveInvite`'s public signature/return type is untouched; the fabrication happens internally when building the stored `FriendRequest`.
- `FriendsRepository.addFriend(Friend)` is a **mock-only convenience method**, not a literal mapping to a real endpoint — a real backend wouldn't need a client-initiated "add to my list" call, since accepting a request already does that server-side. Noted so nobody mistakes it for an intended REST operation later.
- **R-38's "notify the sender when accepted" cannot be demonstrated at all in a single-device mock** and isn't faked: an outgoing request (sent by this device) has no second real device to ever accept it from the other side. Only the *accepting* side's experience (silent accept/decline, matching R-38's "no notification on decline") is testable.
- `FriendAvatar` (`ui/widgets/friend_avatar.dart`) extracted from `friend_list_item.dart`'s previously-private `_Avatar` — this slice needed the identical avatar-or-initials widget for `friend_request_item.dart`, a second real call site being the actual trigger for the extraction, not speculation.
- Entry point: a "Friend requests (N)" row was added directly to `ui/friend_list_page.dart` (above the friends list, shown only when the incoming count > 0) — the **first entry point in this feature that lands directly on the friend list itself**, rather than on `FriendsOnMapStatusView` like every prior one, because this is the first destination real enough to justify it. See the BR-05 tension note below — this is one row toward that eventual restructuring, not the restructuring itself.
- **Known, deliberately-left-alone local WIP as of 2026-09-13**: `entry_point.dart`'s `_openInvite` currently has an uncommitted, unauthenticated early-return bypass in front of its `authAndOpen` gate (added locally to test the deep-link path without a real SSO login, since no dev/QA login bypass exists anywhere in this repo — see the S-07/S-09 creation-half notes above for the same login constraint). This leaves the `authAndOpen` block as dead code, which `flutter analyze` correctly flags as an error when run over the whole package (not scoped to `friends_on_map/`). The user is aware and will remove it by hand — **do not "fix" this without being asked.**

- **R-51 (own position marker) needed zero work.** The 2GIS SDK's built-in "my location" puck — already enabled via `DgisController._setupLocation()`'s `onLocationPermissionGranted`/`toggleFollowState()` — *is* the user's own marker. Exploration mapped exactly how a future real integration would work there (a friends layer would be a normal mutually-exclusive overlay entry, not a satellite-style base-map short-circuit) — worth reusing whenever D-13 resolves, not needed now.
- **R-47's map-corner entry control has nothing to attach to** — this feature has never had a dedicated map-corner button; its only entry point is Profile → Friends on Map. Out of scope for this slice (noted, not dropped); the toggle instead landed on `FriendsOnMapStatusView`, the same "temporary placement, real destination doesn't fully exist yet" pattern every other control in this feature uses.
- `models/friend.dart` gained nullable `latitude`/`longitude` — null means "no visible position," nothing renders. `FakeFriendsRepository`'s 3 seeded sample friends and `FakeFriendRequestRepository.acceptRequest`'s newly-created `Friend` are anchored on the same landmark coordinate `shared/providers/map/dgis_controller.dart`'s `_kingdomTower` constant uses for the map's own default camera position (24.712301, 46.674175 — the app's own "Kingdom Tower, Riyadh" default, not a separately-sourced coordinate), with small ~80-150m offsets — tight enough to land on-screen at the app's default zoom (17), since nothing anywhere fits the camera to the friend markers.
- `providers/friend_markers.dart`: `@Riverpod(keepAlive: true) class FriendMarkers` — watches the layer-visible toggle and the friend list; rebuilds and replaces every marker via `removeAllMarkers()` + `addMarkers()` on a `mapObjectManagerProvider(named: 'friends', layerId: MapObjectLayers.priorityLayerId)` instance (new `MapObjectManagerSettings.friends()` factory). No "move" API exists for a single marker — this is the same remove-then-add-all shape as `features/share_eta/providers/eta_geo_subscriber.dart`, which this slice copied from directly. Photo → `PngBytesMarkerIcon(pngData: img.encodePng(await EtaUtils.processImage(url, 48)))` (reused verbatim, confirmed generic — no ETA-specific coupling); no photo → `SvgMarkerIcon(svgPath: Assets.icons.svg.icProfile2.keyName)`. `onTap` was a no-op in this slice — S-15 (friend card) wires it up in the next slice, see below. Must be watched from somewhere always-mounted to stay alive regardless of which screen is open — `pages/map/map_page.dart`'s `build()` does this in the same cascade as the position reporter.
- **Gotcha hit and fixed in this slice**: `PngBytesMarkerIcon`/`SvgMarkerIcon.width` is `double`, but `EtaUtils.processImage(imgUrl, imgSize)`'s `imgSize` is `int` — the same "48" can't be one shared constant. `friend_markers.dart` uses two: `_kMarkerSizePx` (`int`, for `processImage`) and `_kMarkerSize` (`double`, for marker `width`).
- `providers/friends_on_map_layer_visible.dart`: persisted bool (SharedPreferences key `friends_on_map_layer_visible`), default `true` per Appendix B ("Friends layer default state on first activation: shown"), same shape as `friends_on_map_paused.dart`. No repository — per R-97 this is purely local display state, nothing for a mocked backend to model.
- **Real bug found and fixed after this slice first shipped, caught by manual QA, not by review: markers never actually rendered at all.** `FriendMarkers.build()` originally obtained the shared `mapObjectManagerProvider(named: 'friends', ...)` notifier via `ref.read(...)`. That provider is plain auto-dispose (not `keepAlive`), and `ref.read` doesn't create the keep-alive listener edge `ref.watch` does — so the manager got disposed almost immediately after creation, and every subsequent `manager.removeAllMarkers()`/`addMarkers()` call threw `Cannot use the Ref of mapObjectManagerProvider(...) after it has been disposed`. The fix: `ref.watch` instead of `ref.read`, matching the exact working pattern already used for the `selectedMarker` layer in `pages/map/map_page.dart` (`ref.watch(mapObjectManagerProvider(...).notifier)`). Since `FriendMarkers` is itself `keepAlive` and watched from the always-mounted `MapPage`, watching the manager's notifier transitively keeps it alive for the same lifetime — no more disposal mid-flight. **This is exactly why the try/catch + `logger.log` below exists** — before it was added, this exact exception was a completely silent `AsyncError`, indistinguishable from "markers just aren't rendering," and cost a full round-trip to diagnose from log evidence instead of catching it immediately.
- The `build()` body is wrapped in a try/catch that logs any exception via `logger.log('Error building friend markers: ...')` before rethrowing (state is unchanged, only visibility is added) — this app has **no `ProviderObserver` anywhere** (confirmed by repo-wide grep), so a `keepAlive` provider that's only ever bare-`ref.watch`'d (never `.when()`'d, as `friendMarkersProvider` is in `map_page.dart`) would otherwise fail completely silently. Worth copying this pattern into any other bare-watched `keepAlive` provider in this feature that doesn't already log its own errors (e.g. `friends_on_map_position_reporter.dart`) if a similar mystery ever comes up there.
- **Second real bug, found by the user via manual QA after the disposal fix above shipped: markers appeared only after toggling the layer switch off/on, never on cold start.** Root cause is a pre-existing latent race in `shared/providers/map/object_manager.dart` itself, not specific to this feature: every `MapObjectManager` mutation method (`addMarkers`, `removeAllMarkers`, etc.) is shaped `await ref.read(dgisControllerProvider).value?.foo(..., toManager: await future);` — Dart's null-aware `?.` evaluates the receiver (`ref.read(dgisControllerProvider).value`) synchronously and, if it's `null`, never evaluates the argument list at all (not even the `await future` inside it). `dgisControllerProvider` (`shared/providers/map/dgis_controller.dart`) only resolves once the native map's `onMapCreated` fires, which is guaranteed to be *after* `MapPage`'s first `build()` (where `DgisMap` itself is constructed) — so any `keepAlive` provider that unconditionally mutates markers as the very first thing it does in `build()`, and that's unconditionally `ref.watch`'d from `MapPage` (exactly `FriendMarkers`'s shape), hits a window where the native call is a **silent no-op**: no exception, `_markers` bookkeeping still updates, but nothing is drawn. No other current `mapObjectManagerProvider` consumer hits this — `selectedMarker`/`eta`/`cityscape`/`founding_day`/`leap` all only mutate markers in response to a later action or later in the startup sequence, never unconditionally inside an always-watched provider's first `build()`. **Fix** (scoped to this file only, no changes to the shared `object_manager.dart`): explicitly `await ref.watch(mapObjectManagerProvider(named:, layerId:).future)` right after obtaining the manager notifier, before either branch that mutates it — this waits for the manager (and transitively `dgisControllerProvider`) to fully resolve first, using the same public `ref.watch(xProvider.future)` idiom already used two lines below for `friendsListProvider.future`, rather than reaching for the notifier's own `@protected future` getter. **Worth knowing for whoever builds the next feature that mutates `mapObjectManagerProvider` unconditionally at first build** — this same fix (or making `dgisControllerProvider`-dependent mutations wait properly) would be needed again.
- Verified via a real iOS simulator debug run (`lib/main_dev.dart`, `dev` flavor) after both fixes: clean launch, no crashes, no `Error building friend markers` log line at all. Could not visually confirm the pins render on this session's own sandboxed simulator — its 2GIS map tiles don't render at all in this environment (flat, street-less base map in every screenshot taken this session, both before and after every code change), most likely a sandboxed-network limitation unrelated to this feature's code (same category as this session's pre-existing weather-API TLS handshake failures) — did not affect the user's own testing, where the map renders normally and both bugs were actually caught. Did not tap through the UI myself either way (no tap-automation tooling — `idb`/`idb_companion` aren't installed in this environment); give the user the manual QA checklist for actually confirming markers render immediately on cold start (not just after a toggle) and regress correctly.

## What the S-21 chat slice actually built

Built overnight on branch `feat/BE-213/friends-chat` (app) and `feat/BE-213/friends-chat` in `~/dev/code/wedo/go/balady-friends-service`, by explicit user decision to take the legal risk: BRD open decision **D-15** (minimum age, retention window, whether proactive moderation is required) is **not closed**. The Appendix B values used (2000 chars, 300/h, 60-min delete window, 12-month retention) are the BRD's own provisional ones, overridable on the backend via `LIMIT_MESSAGE_LENGTH`, `LIMIT_MESSAGES_PER_HOUR`, `LIMIT_MESSAGE_DELETE_WINDOW_MINUTES`, `LIMIT_CONVERSATION_RETENTION_DAYS`. Not deployed to Fly; nothing pushed.

- **Backend branch also carries a separate first commit for S-19** (`0fc22b2`): that work was sitting uncommitted on `main` (+353 lines and 3 new files) and a new branch would have dragged it along; it was committed as-is, unchanged, after `go test ./... -race` was green. Chat is the commit on top of it.
- **No conversations table**: a conversation is the (lo, hi) pair of two friends, `messages` rows carry a server `seq` (AUTOINCREMENT) — display order is `seq`, `composedAt` is display-only (API description: a wrong device clock must not be able to insert messages into the past). Sending is `PUT /v1/conversations/{friendId}/messages/{clientMessageId}`, idempotent on the client-supplied id (a replay returns 200 and is not charged against the rate limit) — that is what makes the offline outbox safe.
- Routes: `GET /v1/conversations`, `GET /v1/conversations/{friendId}/messages?before=&limit=`, `PUT …/messages/{clientMessageId}`, `POST …/read`, `POST …/report`, `DELETE /v1/messages/{id}`, `POST /v1/messages/{id}/report`. Event: `conversations_changed` (an invalidation hint like every other event, no payload).
- **R-111/AC-12**: every conversation route answers 404 for "not friends", "blocked" and "no such account" alike. **R-106**: `DeleteMessagesBetween` is called from remove-friend and block (next to the existing `DeleteMeetupsBetween`), so history never resurfaces if the pair become friends again.
- **Delivery states (R-102)**: `delivered` is stamped when the recipient's client actually fetches the thread or the conversation list; `read` only on the explicit `POST …/read`, which the chat screen calls only while it is open and a received message is unread. Unread counts are computed with `COUNT` (read_at null, not deleted, not reported) rather than a maintained counter — the API description warns counters drift after deletion/erasure.
- **R-107**: deleting keeps the row and clears content (`deleted: true`, body/place null) so both sides see a marker. **R-108**: a report is a row in `message_reports` (the operator hand-off; no tooling, D-07) and every read path filters on it for the reporter; reporting a conversation reports every message the friend sent so far (later ones are not covered).
- **Not done**: R-109 (account erasure) — this backend has no account deletion; the deleted-marker path exists via R-107. Push (AC-11, R-126) — no device-token infrastructure exists (S-20 deferred). S-17 meetup was left as it is; a place card is a second message kind (`place_card`), "Open on map" via `ui/open_chat_place_on_map.dart` (deliberately not `openMeetupOnMap`, whose marker tap offers "remove pin" for a meetup that doesn't exist for a chat message).
- **Client**: `models/chat_message.dart`, `conversation.dart`, `outbox_message.dart`; `data/chat_repository.dart` + `remote_chat_repository.dart`; `providers/chat_repository.dart`, `conversations.dart`, `chat_thread.dart` (auto-dispose family, `loadOlder`/`upsert`), `chat_outbox.dart`, `chat_controller.dart` (keepAlive, `ref.mounted` after every await); `ui/conversations_page.dart` (`ConversationsRoute`), `ui/chat_page.dart` (`ChatRoute`, `chat/:friendId`), `ui/widgets/chat_message_bubble.dart`, `chat_input_bar.dart`, `conversation_list_item.dart`. - **Offline outbox (R-103)** (`providers/chat_outbox.dart`): pending messages are JSON strings in a Hive box (`friends_on_map_chat_outbox`) — deliberately **no Hive adapter**, so nothing had to be registered in `entry_point.dart` (which holds the user's local WIP). A network failure/5xx leaves the message pending and stops the flush, so later messages can't overtake it; any other refusal (4xx, a limit) marks only that message `failed` — shown as "not sent", never auto-retried, retried or discarded by the user. Flush triggers: enqueue, opening a thread, socket (re)connect, and automatically on app start if anything is pending.
