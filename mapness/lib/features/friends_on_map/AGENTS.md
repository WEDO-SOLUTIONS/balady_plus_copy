# Friends on Map Notes

This subtree will own the Friends on Map domain (BE-213): consent/activation, location permissions, position reporting, the friend graph (invite/QR, requests, friend list, block), friend markers + friend card on the map, and — if time allows within the timebox — the additive social-layer pieces (reduced meetup, check-ins, shared lists).

## Status

Part A (Foundations) is done. Part B (friend graph) has progressed a lot: friend list (S-11 core), share-my-own-invite (S-07a), scan/open-an-invite → pending request (S-07b + S-09's creation half), and now S-09's *response* half — the requests list, accept/decline/cancel, and R-22 (accepting a request finally adds a real friend to what was, until now, a permanently-static 3-friend sample). S-09 is functionally complete for what a single-device mock can demonstrate. Not started: S-08 (join without the app installed, flagged as first to cut), S-10 (limits), S-12 (block), and all of Part C (map). Read the roadmap below before continuing Part B/starting Part C.

## Scope decisions made 2026-09-09, before any code

Timebox: 2 weeks max including testing. Backend: mocked, not blocking — develop and test against the OpenAPI contract's mock server; the real backend arrives on its own schedule and testing does not wait for it.

- **Chat/messaging (BRD story S-21) is cut** for this iteration.
- **Meetup ("share a place", S-17) is built reduced**: a one-way place-share object outside any conversation thread, not a message type. The full BRD version (R-70, R-117, business rule BR-03 of S-17) specifies the place card as a message living inside a 1:1 conversation, which isn't being built.
- **Push notifications and movement/geofence notifications (S-20, S-22) are deferred.** No device-token registration exists anywhere in the app yet. Per BRD business rule BR-06 (S-11), in-app entry points (the friend list's pending-requests badge) are sufficient without push, so this is safe to defer.
- **Friends layer on the map**: build the BRD's own documented fallback from day one — a toggle inside this feature's own bottom sheet — instead of waiting to confirm whether `features/lifestyle_layers/`'s existing map layers control can accept a new entry (open decision D-13, owner/timeline unconfirmed). Abstract the toggle so swapping to a real layers-control entry later doesn't require rewriting the map screen.
- **Friend positions start as polling** (`GET /v1/friends:positions` every 10-15s) behind an interface, not the full WebSocket channel from the API description. Upgrade later by copying `features/share_eta/providers/eta_websocket_locator.dart`.
- **QR code scanner is in scope for the MVP**, not a stretch item, built from scratch (old scanner code in the app is commented out / removed from dependencies).
- **First thing to cut if part B runs over time**: joining via invite link when the recipient has no app installed yet (store fallback + applying the invite after install, BRD story S-08). Nothing in the app handles that case today.

Full rationale for each of these is in the roadmap artifact above.

## Reusable patterns found elsewhere in this codebase

- Profile-picture marker + moving-marker updates, and a working raw-WebSocket client with a bespoke auth header: `features/share_eta/` (`providers/eta_geo_subscriber.dart`, `providers/eta_websocket_locator.dart`).
- Map-layer registration: `LayerType` enum + `LayersControls` provider in `features/lifestyle_layers/` (satellite/parking/favourites already follow it — see `features/satellite/AGENTS.md` for a worked example).
- Local-first Hive cache with pending add/delete sync: `features/favourites/` — see its own `AGENTS.md` for the pattern in detail.
- A bearer-token Dio interceptor already exists at `shared/lib/auth/auth_token_interceptors.dart` — `AuthTokenInterceptor.tokenInterceptor(ref, baseOptions)`, reusable verbatim: reads `tokenProvider.future` (always-non-null `Future<String>`, empty when logged out), attaches `Authorization: Bearer`, retries once on 401 after `tokenProvider.notifier.refreshToken()`. Three existing call sites (`shared/providers/dgis_network.dart`, `dgis_http_network.dart`, `dgis_hmac_netwrok.dart`) all build a **fresh, feature-scoped `Dio(BaseOptions(baseUrl: ...))`**, not a clone of the shared `baseDioProvider` singleton — that's the convention to follow, not `short_link_repository.dart`'s clone-then-new-Dio approach (also read, but the outlier). The real blocker isn't the interceptor, it's the base URL: `EnvironmentConfig` (`shared/config/environment_config.dart`) has one URL field per backend, sourced from Firebase Remote Config across four env factories (`.urbiDev()` etc.) — a real Friends on Map backend needs a new `friendsOnMapApi` field added there first. Don't build this Dio client until a real endpoint exists to point it at; every repository in this feature is still a mocked in-memory fake.
- Local-first Hive cache, matching `features/favourites/`'s pattern exactly: box via `hiveProvider(boxName)` (`shared/providers/hive.dart`), pending add/delete sync as two `List<T>` keys in the *same* box (not a separate box), next free Hive `typeId` is **6** (favourites uses 2-5, search history uses 1). Adapters are **hand-registered** in `entry_point.dart`'s `initHive()` (~line 1640) — the generated `hive_registrar.g.dart` exists but is dead code, never called; a new Hive model's adapter must be added there by hand. This pattern is deliberately not yet used for the friend list (see "Important Files" below) — it earns its complexity once there's a real add/remove mutation to protect against app-kill-mid-sync, not for a read-only mocked list with nothing to lose.
- BRD requirement R-85 (ETA-mode sharing links) is specified as reusing the temporary-sharing-link mechanism (R-80–R-84) — `features/share_eta/` may already cover a meaningful part of the "temporary/ETA location sharing" story (S-19) independently of the friend graph. Confirm the actual overlap before estimating that piece.

Precisely by BRD story (a correction from this note's earlier draft): R-31 (QR scanner) and R-32 (camera permission) belong to **S-07**; R-29 (create the pending request on resolution) and R-33/R-34/R-35 (error messaging/validation) belong to **S-09**'s creation half; R-36/R-37/R-38/R-22 are S-09's *response* half. ### What the requests-response slice actually built

- Both mocked repositories that hold real mutable state (`friendsRepositoryProvider`, `friendRequestRepositoryProvider`) were switched from plain `@riverpod` to `@Riverpod(keepAlive: true)`. This was a **real bug caught before it shipped**, not a stylistic choice: `friendsListProvider`/the requests providers only kept their repository alive via a `ref.watch` dependency edge that existed *only while a screen was actively watching them* — an accepted friend or a cancelled request would have silently reverted the moment the user navigated away and the underlying auto-dispose repository provider was torn down and rebuilt from its seed data.
- `FakeFriendRequestRepository` seeds **two fixed fake incoming requests** ("Fatima Al-Zahrani", "Khalid Al-Ghamdi") — there's no second real account in a single-device mock to be the sender of an incoming request, same reasoning as the 3 seeded sample friends.
- Outgoing requests (from Scan/deep-link) now carry a **deterministically fabricated display name** (hashed from the token into a small fixed name list) instead of being bare tokens — a real backend's resolve response would include the invite owner's real identity; this is the closest a mock can get without one. `resolveInvite`'s public signature/return type is untouched; the fabrication happens internally when building the stored `FriendRequest`.
- `FriendsRepository.addFriend(Friend)` is a **mock-only convenience method**, not a literal mapping to a real endpoint — a real backend wouldn't need a client-initiated "add to my list" call, since accepting a request already does that server-side. Noted so nobody mistakes it for an intended REST operation later.
- **R-38's "notify the sender when accepted" cannot be demonstrated at all in a single-device mock** and isn't faked: an outgoing request (sent by this device) has no second real device to ever accept it from the other side. Only the *accepting* side's experience (silent accept/decline, matching R-38's "no notification on decline") is testable.
- `FriendAvatar` (`ui/widgets/friend_avatar.dart`) extracted from `friend_list_item.dart`'s previously-private `_Avatar` — this slice needed the identical avatar-or-initials widget for `friend_request_item.dart`, a second real call site being the actual trigger for the extraction, not speculation.
- Entry point: a "Friend requests (N)" row was added directly to `ui/friend_list_page.dart` (above the friends list, shown only when the incoming count > 0) — the **first entry point in this feature that lands directly on the friend list itself**, rather than on `FriendsOnMapStatusView` like every prior one, because this is the first destination real enough to justify it. See the BR-05 tension note below — this is one row toward that eventual restructuring, not the restructuring itself.
- **Known, deliberately-left-alone local WIP as of 2026-09-13**: `entry_point.dart`'s `_openInvite` currently has an uncommitted, unauthenticated early-return bypass in front of its `authAndOpen` gate (added locally to test the deep-link path without a real SSO login, since no dev/QA login bypass exists anywhere in this repo — see the S-07/S-09 creation-half notes above for the same login constraint). This leaves the `authAndOpen` block as dead code, which `flutter analyze` correctly flags as an error when run over the whole package (not scoped to `friends_on_map/`). The user is aware and will remove it by hand — **do not "fix" this without being asked.**

### What the scan/resolve slice actually built

- `mobile_scanner: ^7.4.0` added (first scanning package; `qr_flutter` from the previous slice is generation-only). Resolved cleanly in both `mapness/` and the workspace root — see the dual-`pubspec.yaml` gotcha noted below, hit again and re-confirmed this slice.
- Camera permission reuses `CommonFunctions.checkCameraSettings(BuildContext)` (`lib/app/core/utils/common_functions.dart`, root `balady_plus` package) as-is — it already requests `Permission.camera` and shows `CameraPermissionDialog` on permanent denial. No new permission UI was built.
- `ui/add_friend_page.dart` is now two tabs ("My code" / "Scan"), local widget state (not a route change) — `ScanQrView` is only constructed while the Scan tab is selected, so its `MobileScannerController` (created in `initState`) is torn down (`dispose`) the moment the tab or the whole page is left. This was a deliberate lifecycle decision — a `TabBarView` would have built both tabs' widgets eagerly, firing the camera permission prompt before the user ever chose "Scan".
- `providers/invite_resolution_flow.dart`'s `resolveInviteAndShowResult(context, ref, rawValue)` is the resolution logic for both entry points. It re-parses whatever raw string it's given (a full URL, not a bare token) against `BaldayDeeplink.baseAuthority` — if that parse fails, `InviteResolution.invalidOrBlocked` without ever calling the repository.
- `data/friend_request_repository.dart`'s `resolveInvite({token, ownToken})` takes the caller's own current invite token as a parameter rather than reading `friendsOnMapInviteLinkProvider` itself — keeps the repository dependency-free (matching every other repository in this feature) while still making the self-request check (R-34) genuinely real, not a stub: `providers/invite_resolution_flow.dart` fetches `ownToken` and passes it through.
- **R-35 (duplicate request / already friends) is not modeled** — there is no second real account in a single-device mock to be "already friends" with; every non-self, well-formed token resolves to `success`. Noted here rather than silently absent.
- **R-33's indistinguishability is only partially exercisable**: the mock can only produce `invalidOrBlocked` for genuinely malformed input (wrong host/path shape) — the "reset token" and "blocked owner" cases it's meant to cover require a real backend/second account to fake meaningfully, so only the "unknown format" case is actually testable today.
- **Known gap, deliberately left in place as of 2026-09-09: the two entry points into `resolveInviteAndShowResult` are NOT equally gated.** `entry_point.dart`'s `_openInvite` wraps the call in `authMethodsProvider.notifier.authAndOpen(...)` (per R-29, an authenticated resolver); `ui/widgets/scan_qr_view.dart`'s `_onDetect` calls `resolveInviteAndShowResult` directly, with **no auth gate at all**. This was found while a tester needed to verify resolution logic without a real SSO login available (no dev/QA auth bypass exists anywhere in this repo — checked; only dead, disabled code remnants of one). Decision: leave the scanner ungated for now — it's the only way to test the resolution logic pre-login — and add the matching `authAndOpen` wrap to `ScanQrView._onDetect` (mirroring `_openInvite` exactly) in the same pass as whatever change next needs a real login to verify, rather than fixing it now and re-blocking the only testable path. Don't let this drift — the scanner must eventually be gated the same way the deep link is.

## A BR-05 tension to resolve later, not now

BRD business rule BR-05 (S-11) describes the friend list as "the single in-feature hub" that requests/activity/shared-lists/privacy/notifications are all reached *from* — implying it should eventually **replace** `FriendsOnMapPage`'s post-activation view, not be a screen reached *from* it. Right now it's the other way around: the friend list is one more row on `FriendsOnMapStatusView`, alongside pause/deactivate, for the same reason those are there — no other destination exists yet to justify restructuring around. Revisit this once enough of the hub's rows (requests, activity, shared lists, the real privacy screen) exist to make one restructuring worthwhile, rather than moving the entry point piecemeal on every slice.
